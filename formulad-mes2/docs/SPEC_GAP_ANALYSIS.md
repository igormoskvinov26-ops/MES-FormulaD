# Сверка SPECIFICATION.md с тем, что уже построено

Дата: 27.10.2026. `docs/SPECIFICATION.md` — консолидация устных договорённостей РП (не вся
прочитана из внешних источников, статус рабочий). Этот документ — не пересказ спецификации,
а разница между ней и кодом/решениями, которые уже есть в `formulad-mes2`.

**Дополнение 27.10.2026:** будущая интеграция с 1С ERP — отдельно в `docs/INTEGRATION_1C.md`.

## Главное: меняется масштаб проекта

MVP 0.1 было намеренно **read-only демо на синтетических данных** (`docs/CODEX_START.md`,
п. 0: «никаких CREATE/INSERT/UPDATE/DELETE», «нет подключения к SQL по умолчанию»).
`SPECIFICATION.md` описывает **полноценную MES с операциями записи**: статусы 0–4, запуск/
завершение/FOK сканером, NCP, Rework, входной контроль поставок. Это не продолжение MVP 0.1
по инерции, а следующий этап — он совпадает с тем, что `docs/CODEX_START.md` явно выносил
за рамки (`«Не делать в этом MVP»`, п. 34–37).

**Вывод:** спецификацию принимаем как справочник требований TO-BE, но не как разрешение
писать в PROD или даже в TEST — запрет из `CODEX_START.md` п.0 действует, пока отдельно
не снят. Всё новое пишем сначала на демо-данных, как уже делали для сортировки и
перестановки плана.

## Прямой конфликт с уже построенным кодом

### Перестановка порядка плана — разный UX

Я реализовал (см. `docs/REORDER_DESIGN.md`, код в `PlanScreen.tsx`/`SqlProductionPlanReader`):
**каждый шаг сохраняется немедленно**, одной транзакцией на одно перемещение. Отмены как
отдельного действия нет — есть «отменить последнее перемещение» (симметричный шаг назад).

`SPECIFICATION.md`, раздел 7 **[С]**, описывает другое: отдельный режим
**«Редактировать последовательность»**, в котором можно накопить несколько перемещений
(стрелки + ввод номера позиции), а затем явно нажать **«Сохранить новую последовательность»**
или **«Отменить изменение»** (откат к состоянию на момент входа в режим).

Это не частность — разная модель транзакций:
- моя версия: N перемещений = N операций записи, не связанных друг с другом;
- версия спецификации: N перемещений = один черновик, одна операция публикации, один явный отказ.

У второй модели есть то, чего нет у первой: **безопасный откат всей серии** без ручной
отмены каждого шага, и более ровная работа при нескольких диспетчерах — конфликт проверяется
один раз при сохранении, а не на каждом шаге.

**Решено РП 27.10.2026:** остаётся немедленное сохранение каждого шага (текущая реализация).
Режим «черновик + явные Сохранить/Отменить» из `SPECIFICATION.md` раздел 7 **не делаем** —
это осознанное расхождение с консолидированной спецификацией, а не недосмотр. Если сценарий
«перекроить план целиком одним заходом» станет частым, вопрос можно пересмотреть.

### Статусная модель

`SPECIFICATION.md` фиксирует формальные статусы `0`–`4` с именами и переходами. Это не
противоречит `docs/AS_IS_FACTS.md` (там `statusid` — int, реально существует), но раньше
проект сознательно избегал *придумывать* enum поверх строкового `Status`
(`CODEX_START.md`, п.3: «не придумывать универсальный enum и не переписывать значения»).
Теперь модель не придумана мной, а зафиксирована как **[С]** — это снимает прежнюю
осторожность для статусов 0–4 конкретно, но правило «неизвестные значения не ломают UI»
(бейдж «Другое: …») остаётся обязательным: в реальной базе наверняка есть значения вне 0–4
(архивные, временные, ошибочные).

## Что уже готово и совпадает

- **VIN как ключ, без выдуманного ID-ключа** (раздел 4) — уже так в API и демо-ридере.
- **Сортировка плана по позиции, не по VIN** (раздел 7, подтверждено вами ранее) — реализовано.
- **NCP как отдельная сущность, привязанная к VIN** (раздел 14) — начатая, но не подключенная
  заготовка `Ncp.cs` ближе к этой модели, чем я думал: там уже есть компонент, количество,
  тип, комментарий, автор/время. Чего не хватает против раздела 14: **операторский и
  инженерный комментарий отдельно** (у меня один общий `Comment`), **статус «есть ли
  корректная деталь»** отдельно от статуса самой заявки, и **станция**, на которой нашли
  несоответствие (я станцию не закладывал — см. ниже).
- **Ничего не редактируется из таблицы плана** (раздел 6.2: исправление через карточку
  строки/справочник, не произвольная ячейка) — совпадает с тем, что я закладывал для NCP
  и с отказом от инлайн-редактирования, который мы уже обсуждали на AS-IS скриншотах.

## Новое, чего в проекте пока нет вообще

Коротко, без оценки трудозатрат — просто перечень разделов спецификации без кода:

- Импорт плана из Excel + временная таблица + построчная валидация (разделы 6, 29 AT-01…AT-07).
- JobCard: печать одной/группой, QR (раздел 8).
- Сканер-сценарий «первый скан = поиск, второй скан/кнопка = подтверждение», звуки (раздел 9).
- Запуск/Завершение/FOK как операции записи по статусам 0→1→2→3 (разделы 10, 13, 18).
- Станции как рабочий объект (а не только атрибут справочника): визуальная линия, проверка
  комплектующих по станции, завершение станции (раздел 11) — зависит от В-15/В-16.
- Rework как отдельный статус `4` и экран (раздел 17).
- Входной контроль целиком: поставки, упаковки, HU, норматив контроля, закрытие коробки/
  поставки (разделы 19–24) — не начато.
- Журнал событий/аудит (раздел 25).

## Станция в NCP: решение нужно сейчас, а не потом

Раздел 14 требует указывать станцию при регистрации NCP. Моя заготовка `Ncp.cs` станцию не
хранит. Поскольку NCP — следующая задача по вашим словам, лучше добавить поле станции сразу,
а не переделывать после. Но поле станции осмысленно только если есть откуда брать список
станций для выбора — а это справочник, которого в демо-фикстурах тоже пока нет
(`docs/PRINTED_CARDS.md` зафиксировал, что станция есть у *операций* в AS-IS, но не как
отдельный независимый справочник в наших данных).

## Открытые вопросы спецификации, которые сразу бьют по следующему шагу (NCP)

Из раздела 30, приоритет A, применимо к NCP прямо сейчас:
- **В-20**: можно ли несколько NCP на один артикул/станцию на одно изделие, как фиксировать
  частичную замену (1 из 3 шт).
- **В-22/В-23**: что именно закрывает «рисковый» признак (незакрытая доустановка) — отметка
  об установке, закрытие NCP, или оба.

Без ответа на них нельзя корректно спроектировать статус заявки NCP (не только «Открыто/
В работе/Закрыто», как у меня сейчас, а «Открыто / корректная деталь не установлена /
установлена / закрыто»).

## Предложение по следующему шагу

1. Зафиксировать решение по UX перестановки плана (немедленное сохранение vs. явные
   Сохранить/Отменить) — минимальная правка, но лучше сделать один раз.
2. Доделать NCP с полями из раздела 14 (станция, раздельные комментарии оператора/инженера,
   признак установки детали) на демо-данных — это расширяет уже начатую работу и не требует
   ответов на входной контроль/Rework/JobCard.
3. Остальные крупные блоки (импорт плана, JobCard, сканер-сценарии, входной контроль) —
   по вашему приоритету; каждый достаточно велик, чтобы делать отдельным заходом, а не все
   сразу.
