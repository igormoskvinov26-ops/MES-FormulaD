# Главная задача Codex: реализовать FormulaD MES 2.0 — MVP 0.1

Ты — ведущий full-stack разработчик промышленной MES. Прочитай все файлы `docs/*`, а затем реализуй код в текущем репозитории. Пользователь — РП проекта, ему нужен воспроизводимый результат и простые объяснения на русском языке. Не превращай документацию в бесконечное обсуждение: работай над **первым запускаемым локально MVP**.

## 0. Непреодолимые запреты

- **Никогда не подключаться к PROD** `SQLACCESS` или базе `FormulaD` в ходе текущей задачи. Не выполнять сетевую разведку/проверку подключения даже в режиме SELECT; на этой итерации только DEMO.
- Никаких `CREATE`, `ALTER`, `DROP`, `INSERT`, `UPDATE`, `DELETE`, `MERGE`, `TRUNCATE`, `BACKUP`, `RESTORE`, `CHECKPOINT`, `SHRINK`, `DBCC` и никаких созданий SQL-логинов. Даже в документации не предлагай команды, изменяющие PROD.
- Не копировать или импортировать реальную Access-базу и не размещать её экспорт в репозитории.
- Не брать логины/пароли из `tblUser`, VBA, ODBC строк или данных пользователя. Никаких секретов в репозитории и выводах.
- Нет подключения к SQL по умолчанию: настройка `DataSource=Demo`; режим SQL должен завершаться контролируемой ошибкой конфигурации, если не указан явный тестовый экземпляр/подключение с read-only учётными данными. Не реализовывать fallback с Demo на PROD.
- Не добавлять обработчики изменения производственных данных. Только `GET` API для чтения производственных данных (и отдельная dev-авторизация, если потребуется).
- Никаких служб Windows, изменений портов, firewall, IIS, установки на ВМ в этой итерации.

## 1. Технологии

- `backend`: ASP.NET Core на **.NET 10 LTS**, C#, Minimal API (или контроллеры при мотивированном выборе), DI, typed DTO, `CancellationToken`, встроенное логирование; OpenAPI только в Development. Готовность к Windows Service **на будущее**, но сейчас не регистрировать службу.
- `frontend`: React + TypeScript + Vite, удобный интерфейс на русском, минимальные зависимости, адаптация для экранов оператора, клавиатуры/сканера.
- `SQL`: Microsoft SQL Server 2019 Enterprise. На будущей тестовой интеграции предпочтительно `Microsoft.Data.SqlClient` с параметризованными `SELECT`, явным белым списком колонок и `TOP/OFFSET` пагинацией; Dapper допустим, если обоснован. Не использовать `EF Migrations`/`EnsureCreated`.
- `tests`: .NET unit/integration для endpoints и репозитория, frontend unit tests; если доступен Playwright — E2E smoke. Не добавлять Docker/Kubernetes/Redis/microservices.
- В прод-перспективе единое ASP.NET Core приложение сможет отдавать скомпилированные файлы React. В режиме разработки Vite может проксировать `/api` на localhost .NET API.

## 2. Объём MVP 0.1

Сделать:
1. Русскоязычный UI в индустриальном стиле: основной экран «Производственный план», общий поиск VIN (ввод с клавиатуры и сканера), таблица, карточка VIN, фильтры по статусу, пагинация, состояния загрузки/ошибки/пустой выдачи.
2. Серверный API с контрактом `docs/API_CONTRACT.md` и реализацией через `IProductionPlanReader` (`DemoProductionPlanReader` сейчас, будущий `SqlProductionPlanReader` в отдельной задаче). Не требовать SQL Server для первого запуска.
3. Защищённый backend access. Для DEMO разрешён только **явно включаемый Development auth mode** с учётной записью, настроенной через user-secrets или env, без пароля по умолчанию/в исходниках. Защищённые GET-эндпоинты должны возвращать `401` без аутентификации. Используй защищённый cookie-сеанс либо равнозначный механизм; для production auth — заглушка fail-closed (никакой пользователь из `tblUser` автоматически не авторизуется). Не публикуй dev mode вне loopback.
4. API чтения плана, одной карточки, списка доступных статусов; health liveness (минимум метаданных).
5. Типизированные DTO, валидация параметров, ограничение pageSize, сортировка, единообразные ошибки (ProblemDetails). Отсутствие записи в БД.
6. Демо-данные *только* из `fixtures/production-plan.demo.json`: явно синтетические VIN, разные статусы, пустые даты и заполненные даты, без персональных данных.
7. Тесты, `.gitignore`, `.env.example` без секретов, `README.md` с командами запуска на macOS и ожидаемым выводом, `docs/IMPLEMENTATION_REPORT.md` с итогом и фактическими тестами.

Не делать в этом MVP:
- Импорт Excel, создание/изменение производственного плана, запуск/завершение/ФОК, QR-инспекторы, QC events, NCP/cripple, Packing Lists, печать, 11 станций, приёмка ОТК, настоящие пользовательские учётные записи.
- Любые миграции БД и экраны реального администрирования.
- Никакой production deployment.

## 3. Важнейшие факты схемы, нельзя угадать иначе

- `dbo.tblProductionPlan.VIN` — **PRIMARY KEY**, `nvarchar(50)` (`sys.columns.max_length = 100` *байт*).
- `dbo.tblProductionPlan.ID` — `int NOT NULL`, но **не PK, не IDENTITY, нет обнаруженного UNIQUE-индекса**; дублей в обследованной базе не было. По `ID` НЕ делать роуты, поисковые ключи или FK.
- `dbo.tblProductionPlan.rv` — `rowversion/timestamp`, **не дата-время**.
- `dbo.tblProductionPlan.shipment_comments` — `datetime`, несмотря на имя. В этом MVP поле не нужно.
- Статусы базы — реальные строки `Status` и `statusid`; не придумывать универсальный enum и не переписывать значения. Цветные бейджи UI могут классифицировать лишь известные значения, неизвестные — «Другое» с оригинальным текстом.
- `tblQC_Products` — другая сущность с собственным `ProductID` и UNIQUE VIN, но без FK на `tblProductionPlan`. Не смешивать без отдельного проектирования.

## 4. Порядок выполнения

A. Сделай короткую структуру решений (5-10 абзацев максимум), сверяясь с docs. Затем сразу создавай файлы.
B. Собери backend и frontend с демо-репозиторием; обеспечь успешный запуск локально.
C. Добавь тесты, проверь команды `dotnet build`, `dotnet test`, `npm run build`, необходимые E2E по возможности. Если инструмент не установлен — честно укажи, что проверка не запускалась.
D. Проверь отсутствие SQL secret/prod endpoints и любых HTTP-операций записи бизнес-сущностей. Сгенерируй `docs/IMPLEMENTATION_REPORT.md`: что сделано, архитектура, чем проверено, как запустить, открытые ограничения.
E. Приложи понятные скриншоты интерфейса **только если есть реальный браузер/рендер и это действительно было проверено**.

## 5. Критерии завершения

**Нужна работающая программа на вымышленных данных**, а не исключительно проектная документация. Пользователь может открыть локальную страницу, войти через явно настроенную dev-учётную запись, увидеть план, найти VIN и открыть карточку. При отключённой dev-аутентификации доступ к защищённым endpoints закрыт. Нет ни одной попытки подключения к PROD.

Извлекать настоящие пароли, пробовать подключиться к существующему корпоративному серверу, предлагать остановить SQL Server, исправлять старую схему — категорически нельзя.
