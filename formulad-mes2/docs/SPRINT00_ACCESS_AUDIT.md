**Источник:** архив выгрузки `MES_ASIS_20261026_142202(1).zip` из локальной копии `MES_COPY.accdb`.  
**Режим работы:** автономный статический анализ файлов. SQL-запросы не выполнялись, рабочая база данных не изменялась.  
**Стадия:** предварительный аудит AS-IS; рабочее поведение нужно проверить на тестовом стенде.

## 3. Подтверждённые риски и особенности (без изменений PROD)

### R-01. Неатомарный импорт производственного плана — высокий риск
**Источник:** `forms/0018_frmPPcheck.txt`, обработчик `Кнопка19_Click`.

После проверки `qtyerrors` обработчик перебирает записи `tblImportplan`, по одной вызывает `AddNew/Update` в `tblProductionPlan` и после успешного цикла удаляет записи из `tblImportplan`. Общей транзакции `BeginTrans/CommitTrans/Rollback` в этом обработчике не видно. При ошибке после нескольких вставок возможен частично загруженный план. Указанная в коде отчётная переменная `lngCount` может отражать число попыток, а не гарантированно успешно завершённых вставок.

**Решение в TO-BE:** пакет импорта с идентификатором загрузки, полностью серверная повторная валидация, атомарное утверждение/загрузка, журнал результата и безопасная обработка повторного импорта.

### R-02. Общая область импорта и перестановки очереди — высокий риск
**Источники:** `tables_fields.tsv`; `forms/0001_frmChangePP.txt`; `forms/0018_frmPPcheck.txt`; `forms/0041_frm_Start.txt`.

`tblImportplan` и `tblPlanTemp` — ODBC-связи с SQL Server. В `frmChangePP` выполняются `DELETE FROM tblPlanTemp` и последующая вставка данных для изменения очереди. При совместном использовании возможны пересечения сеансов операторов. В формах перестановки позиции несколько отдельных `UPDATE` выполняются без общей транзакции; ошибка между ними может оставить частично обновлённую последовательность.

**TO-BE:** уникальный `ImportBatchID`/сеанс при импорте; для перестановки — серверная операция внутри транзакции с блокировками/проверкой версии.

### R-03. Старт сборки может переписать первоначальную дату — высокий риск
**Источник:** `forms/0041_frm_Start.txt`, `txtSearchVIN_AfterUpdate`.

После нахождения VIN выполняется `UPDATE tblProductionPlan SET StartDate=Now(), Status='in progress', statusid=1 WHERE VIN=...` без условия, что изделие ещё не стартовало. Сообщение об успешном запуске показывается **до** фактического выполнения `CurrentDb.Execute`. Возможны повторная запись времени и ложное позитивное сообщение при ошибке.

**TO-BE:** проверка допустимого текущего состояния и условное обновление в одной транзакции; ответ «уже начато» без перезаписи; подтверждение успеха только после фиксации БД.

### R-04. Завершение сборки недостаточно защищено правилами переходов — высокий риск
**Источник:** `forms/0042_frm_Complete.txt`, `txtSearchVIN_AfterUpdate`.

По найденному VIN форма ставит `CompleteDate=Now`, `Status='complete'`, `statusid=2`. В обработчике не видно обязательной серверной проверки старта, открытых NCP и повторного завершения. Отсюда **не следует**, что вся MES лишена таких проверок: надо проверить ограничения и фактический сценарий.

**TO-BE:** формальная машина состояний и серверные проверки до изменения.

### R-05. ФОК подтверждается без явного идентификатора инспектора в обработчике — высокий риск
**Источник:** `forms/0043_frm_FOK_list.txt`, `btn_fok_Click`.

Код проставляет `Status='FOK'`, `FOK_date=Now`, `statusid=3`. В этом обработчике не обнаружены сканирование карточки инспектора, создание события в `tblQC_Events` или запись подписи в новый QC-реестр. Существующие таблицы `tblQC_*` в данных SQL пока пустые, кроме справочника точек.

**TO-BE:** отдельное проверяемое подписание контрольных операций с аудитом и разграничением ролей; старую и новую модели согласовать.

### R-06. Проверки прав в основном на уровне интерфейса — высокий риск
**Источники:** `forms/0023_frmMain.txt` (`Form_Load`); `forms/0002_frmNCP.txt` (`Form_Load`); `forms/0001_frmChangePP.txt`.

В некоторых местах роль определяется по `Environ("USERNAME")`, а для «неадминистратора» просто скрываются кнопки. В одном обработчике обнаружен **встроенный в VBA статический код доступа** (его значение намеренно не воспроизводится в отчёте). Это не заменяет разграничение прав на сервере; код доступа нужно считать скомпрометированным при распространении исходников.

**TO-BE:** аутентификация сервера, роли на API, отдельный SQL-логин с минимальными правами, журналирование. Проверить и при необходимости заменить встроенные секреты.

### R-07. Формула заполнения `tblProductionPlan.ID` не установлена — высокий риск перед миграцией
**Источники:** SQL-схема из предыдущих проверок; `forms/0018_frmPPcheck.txt`.

`tblProductionPlan.VIN` — PK; `ID` не PK, не IDENTITY, UNIQUE-индекс для него не обнаружен, фактических повторов нет. Импорт `frmPPcheck` заполняет VIN и другие поля, но не назначает `ID`. Требуется изучить `DEFAULT`/вычисление ID и фактический результат импорта. Не менять схему до этой проверки.

### R-08. Некоторые определения выглядят устаревшими или с отсутствующими зависимостями — средний риск
**Источники:** определения форм и `tables_fields.tsv`.

Форма `frmStations` ссылается на `tblStation`, которой нет среди 34 объявленных таблиц Access в выгрузке. Форма `frmRegistration` использует источник `dbo_tool_users`, которого также нет среди объявленных таблиц. В коде ряда форм встречается ссылка на `frmNcpCreate`, а такая форма в списке 46 не обнаружена. Это **кандидаты на неиспользуемую/сломанную логику**, не доказательство неисправности основных производственных функций.

**TO-BE:** классифицировать каждую форму как активно используемую, резервную или архивную; в MVP переносить только подтверждённые сценарии.

### R-09. Необходимо различать «backup-таблицы» и настоящие резервные копии — высокий риск
**Источники:** `queries/0021_SQL_backup.sql.txt`; `forms/0023_frmMain.txt`.

Запрос с именем `SQL_backup` содержит удаление и вставку в `*_backup` таблицы. Его вызов из `frmMain` находится в комментарии. Это не полноценный backup SQL Server; **не запускать данный запрос в PROD**.

**TO-BE:** проверить штатные полные, дифференциальные и журнальные копии SQL Server. Для БД `FormulaD` ранее установлен режим восстановления `FULL`.

### R-10. Изменяемое определение общего сохранённого запроса — средний риск
**Источник:** `forms/0040_frm_Packs.txt`, `Form_Load`.

Форма перед открытием списка упаковок переписывает SQL определения `qry_Packing_Packs` под выбранный `PL_id`. Статический текст запроса в выгрузке содержит фильтр `PL_id=4`, который заменяется кодом формы при открытии. Этот приём делает результат зависимым от состояния файла фронтенда; особенно проблемен, если один файл Access используется несколькими пользователями.

**TO-BE:** параметризованный API-запрос, `PL_id` в адресе/параметре; не перезаписывать общую SQL-дефиницию.

### R-11. Текущий «cripple» — преимущественно представление открытых несоответствий — средний риск
**Источники:** `queries/0003_qry_cripple.sql.txt`, `queries/0024_SQL_qry_cripple.sql.txt`, `forms/0034_frm_Cripple.txt`, SQL-инвентаризация `tblCrippleRecord=0`.

Выборка фактически строится на `tblNCP`, связанном с `tblProductionPlan`, и статусе NCP. Отдельная сущность `tblCrippleRecord` существует, но по текущей инвентаризации пустая. Правило «нет замены → обязательная регистрация cripple» в проанализированных обработчиках не подтверждено.

**TO-BE:** вместе с производством определить статусы/причины/регистрацию и снятие с cripple; не дублировать сведения NCP.

### R-12. Проверка импорта распределена между Access и SQL — средний риск
**Источники:** `queries/0008_qryCheck.sql.txt`, `queries/0025_SQL_qryCheck.sql.txt`, ранее предоставленное `dbo.vwImportCheck`, `forms/0018_frmPPcheck.txt`.

Обнаружены несколько реализаций проверок. Некоторые возвращают полную запись с флагами ошибок, другие могут по-разному обозначать удачный/ошибочный результат. Окончательную версию правил нужно определить по активному маршруту пользователя.

## 4. Наблюдения по технологической архитектуре

- В Access действуют **31 ODBC-подключение** к таблицам SQL; новые `tblQC_*` в экспортированном списке связанных Access-таблиц отсутствуют. Следовательно, в текущем фронтенде нельзя предполагать работающий полноценный новый QC-модуль только из наличия структур SQL.
- Отдельные контрольные события (начало/завершение/ФОК) хранятся в полях `tblProductionPlan`; данные по дефектам — `tblNCP`; входной контроль — `tblPL_Lines`.
- Работа со сканерами построена в основном на событиях `AfterUpdate` полей формы с последующим поиском через `FindFirst`. При миграции нужно сохранить удобство работы сканером, но сделать серверные операции повторно-безопасными.
- Печать отчётов тесно зависит от запросов Access, функции `Code_128` и `TempVars` (например, `PP_id`). Для Web MES потребуется отдельно определить технологию печати на рабочих местах.
- В выгрузке имеются несколько похожих/дублирующихся форм; их не следует механически переносить в React по принципу «одна форма = одна страница».

## 5. Приоритеты для проекта (рекомендуется)

1. **Заморозить модель AS-IS**: сохранить архив и версии схемы отдельно от PROD, ограничить доступ к коду/секретам.
2. **Проверить эксплуатационные ограничения**: ОС ВМ, версии и резервные копии SQL, права пользователей и драйверы ODBC.
3. **Зафиксировать реальный пользовательский путь** по каждому процессу: импорт, старт, завершение, ФОК, NCP, Packing Lists, печать; отличить используемое от архивного.
4. **Спроектировать базовый API на чтение** для производственного плана, VIN-карточки и справочников; пока без операции записи и без модификаций PROD.
5. **Согласовать единый механизм операций записи**: транзакции, защита от дублей, допустимые переходы статусов, аудит, учёт пользователя, гарантия совместимости с аварийным Access.
6. **Перенести сценарии** последовательно: план и VIN → старт/завершение → ОТК → NCP/cripple → входной контроль → печать и аналитика.
