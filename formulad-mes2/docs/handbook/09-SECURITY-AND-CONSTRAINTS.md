## 1. Постоянный запрет на PROD

> **PROD (`SQLACCESS` / база `FormulaD`) не подключается никогда.** Это не отдельный дальний этап, а **постоянный запрет**
> (`docs/DEVELOPMENT_PLAN.md`, этап 11; `docs/CODEX_START.md`, п. 0).

Что это значит на практике:

- Приложение, тесты, скрипты и ИИ-агенты **никогда** не подключаются к базе `FormulaD` ни на чтение, ни на запись.
- Допустима только отдельная тестовая база **`FormulaD_TEST`**.
- Административные учётки (`sa`, `sa1`) не используются нигде.
- Запрет действует и на PROD-контур 1С, если он появится (`DEVELOPMENT_PLAN`, этап 12).

**Почему.** В `FormulaD` нет подтверждённого резервного копирования: `msdb.dbo.backupset` пуст, заданий резервного
копирования в SQL Agent нет, восстановление не проверялось (риск **R-001**, `AS_IS_FACTS`). Любая ошибка в PROD
необратима. Возможность технически развернуть приложение на сервере **не является** разрешением на ввод в эксплуатацию
(`SECURITY_AND_DEPLOYMENT.md`).

**Важная тонкость: сервер один.** `SQLACCESS` — ВМ Windows Server 2019, на которой **вместе** стоят `FormulaD` (PROD) и
`FormulaD_TEST` (`sql/create-test-db.sql` создаёт TEST «на PROD-экземпляре»). Поэтому запрет сформулирован по **базе данных**,
а не по имени хоста: подключение к хосту `SQLACCESS` с `Initial Catalog=FormulaD_TEST` разрешено (это закреплено тестом
`Accepts_Prod_Host_With_Test_Database`), подключение к базе `FormulaD` — нет.

## 2. Как запрет обеспечен в коде

Все проверки — в `src/FormulaD.Mes.Api/SqlOptions.cs` (`SqlOptions.Create`), вызываются при старте и при ошибке бросают
`InvalidOperationException` (приложение не запускается).

| № | Барьер | Где | Что делает |
|---|---|---|---|
| 1 | **Источник данных** | `Program.cs` | Приложение работает только с SQL Server; строка подключения обязательна |
| 2 | **Строка подключения только извне** | `SqlOptions.Create` | `Sql:ConnectionString` обязана быть задана (user-secrets/переменные среды); в репозитории её нет |
| 3 | **База обязана быть указана** | `SqlOptions.Validate` | Пустой `Initial Catalog` → отказ (иначе соединение попало бы в «базу по умолчанию» логина) |
| 7 | **Read-only намерение** | `SqlOptions.Create` | Строка для чтения получает `ApplicationIntent=ReadOnly`; таймаут соединения ≤ 15 с; `ApplicationName` помечен |
| 8 | **Параметризованный SQL** | все `Sql*.cs` | Параметры `SqlParameter`, фиксированные имена `[dbo].[tbl…]`, без динамических имён объектов, без трёхчастных имён и `USE` (проверено поиском по коду) |
| 9 | **Логи без секретов** | `Program.cs` | Пишется только имя источника данных, не хост/база/учётка |

> **Обновление.** Программные барьеры (`ForbiddenDatabases`, `ForbiddenLogins`, `IsTestEnvironment`) **удалены** — production-сервер
> физически изолирован в отдельной сети (из среды разработки подключение к PROD невозможно).

**Остаточные риски (держать в голове):**

1. **Одна учётная запись на чтение и запись.** `Sql:ConnectionString` используется и для чтения (с `ReadOnly`), и для записи
   (без `ReadOnly`) — логин обязан иметь права записи, поэтому «логин только с SELECT», как сказано в устаревших документах,
   **больше не соответствует коду** (**T-003**).
2. **Создание таблиц приложением.** `SqlStationChecks` и `SqlIncomingInspection` при первом обращении создают таблицы
   (`EnsureTables`: `tblComponentCheck`, `tblIncoming*`, `tblInspectionQuota`), для чего логину нужны DDL-права (`db_ddladmin`) —
   хотя скрипт выдачи прав оговаривает только DML. Нужно сознательно решить, кто и когда создаёт эти таблицы (**T-004**).
3. **SQL-скрипты в `sql/` затрагивают PROD.** `export-schema-from-prod.sql` (только чтение метаданных) и `copy-prod-to-test.sql`
   (читает PROD `FormulaD`, перезаливает данные в `FormulaD_TEST`) — это **ручные административные скрипты DBA**, не часть
   приложения. Их нельзя запускать из автоматизации и ИИ-агентам.

**Тесты** (`tests/…/SqlReaderTests.cs`, без SQL Server): отказ без строки подключения; принудительный `ReadOnly`;
параметризация, отсутствие `SELECT *` и `NOLOCK`.

## 3. Dev-аутентификация

Временный механизм, пока не выбран корпоративный identity-provider (вопрос 1 `OPEN_QUESTIONS`, **В-04**). Реализован в
`Program.cs` и `Models.cs` (`DevAuthOptions`).

**Условия существования входа.** Маршрут `POST /api/v1/dev-auth/login` **регистрируется только если выполнены все условия**:

1. `ASPNETCORE_ENVIRONMENT=Development` (иначе `Enabled` принудительно `false`);
2. `DevAuth:Enabled=true`;
3. заданы `DevAuth:Username` и `DevAuth:Password` (из переменных окружения или user-secrets).

Иначе маршрута **нет физически** (`404`), а все защищённые эндпоинты отвечают `401`. В лог при старте пишется
предупреждение «Dev-аутентификация выключена».

**Защита самого входа.**

| Мера | Реализация |
|---|---|
| Только локально | `IsLoopback(ctx)`: адрес клиента — loopback (или не определён) |
| Только свой origin | `IsSameOrigin(ctx)`: заголовок `Origin` пуст (curl/тесты) либо loopback/`localhost` |
| Сравнение пароля | `CryptographicOperations.FixedTimeEquals` над UTF-8; логин — `StringComparison.Ordinal` |
| Нет пароля по умолчанию | пароль только извне; в `appsettings.json` — `DevAuth:Enabled=false` |
| Cookie | `formulad.mes.session`: `HttpOnly`, `SameSite=Strict`, `Secure` **вне Development** (в Development — `SameAsRequest`); срок 8 ч, скользящий |
| API без редиректов | вместо перенаправления на логин — `401`/`403` |

**Что даёт аутентификация.** Только имя пользователя (claim `Name`, `auth_mode=dev`) для журнала и событий. Ролей и прав нет.

> **Последствие для развёртывания.** Из-за условия «только Development» и «только loopback» сетевой доступ с других ПК
> через DevAuth невозможен. Для настоящей эксплуатации нужен корпоративный провайдер (AD/OIDC) — это отдельная задача
> ([13](13-ROADMAP-AND-KNOWN-ISSUES.md)). Пример `deploy/appsettings.Production.example.json` включает `DevAuth`, но в
> окружении Production код его **выключает**: после установки службы по `deploy/` войти нельзя
> ([11](11-OPERATIONS-AND-STAND.md#4-развёртывание-как-служба-windows)).

## 4. Секреты и конфигурация

**Правила.**

1. **Ничего секретного в git:** ни паролей, ни строк подключения, ни токенов, ни `.env`, ни `appsettings.Production.json`,
   ни баз, ни выгрузок Access/VBA, ни PIN. `formulad-mes2/.gitignore` уже исключает `.env`, `.env.local`,
   `appsettings.Production.json`, `appsettings.*.local.json`, `stand/.run/`.
2. **Откуда брать секреты:** переменные окружения (`DevAuth__Password`, `Sql__ConnectionString`) или `dotnet user-secrets`
   (`UserSecretsId = formulad-mes2-api`).
3. **Примеры** — только с заглушками (`CHANGE_ME`, `<ваш локальный пароль>`).
4. **Логи не содержат**: строку подключения, пароли, PIN, номера двигателей и полные VIN «по умолчанию»
   (`SECURITY_AND_DEPLOYMENT`). Сейчас в журнал событий попадают VIN как ключ сущности — учитывать при выводе журнала наружу.
5. **Пароль стенда** генерируется заново при каждом `stand.sh up` и хранится в `stand/.run/credentials` (`chmod 600`),
   в git не попадает. Не публикуйте его в чатах и тикетах.
6. **Нельзя** использовать `tblUser.PasswordHash`, пароли и PIN из Access/ODBC/VBA; не пересылать оригиналы Access без
   корпоративной проверки и обезличивания.

**Заметка.** В `sql/create-writer-login.sql` и `deploy/appsettings.Production.example.json` стоит заглушка `CHANGE_ME` —
это допустимо (реальный пароль подставляется на сервере). В `sql/create-test-db.sql` запуск предполагается «под `sa1`» —
это инструкция для DBA на сервере; приложение и разработчики `sa1` не используют.

## 5. Модель угроз

Краткая, по компонентам. Границы доверия: браузер ↔ API; API ↔ SQL; репозиторий ↔ внешний мир.

| Угроза | Вектор | Мера | Остаток |
|---|---|---|---|
| Подключение к PROD | Неверная строка подключения, случайный запуск скрипта | Физическая изоляция сети; конфигурация окружений; права логина | Production-сервер недоступен из среды разработки |
| Несанкционированный доступ к API | Прямой запрос без входа | `RequireAuthorization()` на всех бизнес-группах; `401` | Вне Development входа нет вовсе (закрыто) |
| Подбор пароля DevAuth | Перебор | loopback + same-origin; сравнение за постоянное время | **Нет ограничения числа попыток** (rate limiting) — допустимо только из-за loopback |
| CSRF | Подмена запроса с чужого сайта | `SameSite=Strict`; на login — проверка `Origin` | Отдельных antiforgery-токенов нет (комментарий в коде: добавить при не-loopback входе) |
| XSS | Данные из Excel/NCP-комментарии | React экранирует строки по умолчанию; `dangerouslySetInnerHTML`, `eval`, `innerHTML` в `apps/web/src` не найдены (проверено поиском) | Печатные формы собираются из тех же данных |
| SQL-инъекция | VIN, комментарии, пересылаемые строки | Только параметризованный T-SQL; тесты на отсутствие конкатенации и `SELECT *`; экранирование `LIKE` | `$"""…"""` в SQL-текстах используется для подстановки **констант** (списки колонок) — не вставлять туда пользовательский ввод |
| Утечка секретов | Коммит `.env`, строк подключения | `.gitignore`, ревью, чек-лист | Нет автоматического сканера секретов в CI *(CI не настроен)* |
| Подмена/потеря данных | Два пользователя правят одно | Условный `UPDATE … WHERE statusid=@from` | Нет `rowversion` для перестановки/NCP (AT-30) |
| Отсутствие аудита | «Кто это сделал?» | `IEventLog` вызывается во всех операциях записи | Журнал **в памяти**, не хранится, не отдаётся пользователю |
| Отказ в обслуживании | Огромный ввод | `pageSize ≤ 100`, длина VIN ≤ 50 | Лимитов на размер вставки Packing List/импорта в коде не найдено |
| Повышение привилегий | Рядовой пользователь делает всё | — | Ролей нет (см. раздел 6) |

## 6. Известные пробелы безопасности

1. **Нет ролей** — любой вошедший может выполнять любые операции, включая закрытие NCP, публикацию плана, закрытие поставок.
2. **Нет корпоративной аутентификации**; DevAuth не годится для сетевой эксплуатации.
3. **Журнал событий не сохраняется** и недоступен пользователю (раздел 25 спецификации не выполнен).
4. **Нет rate limiting и antiforgery** (приемлемо только на loopback).
5. **Служба Windows** (`deploy/install-service.bat`) создаётся командой `sc create … start=auto` без `obj=` — запускается под
   учётной записью по умолчанию `LocalSystem` (высокие права). *(Следует из скрипта; фактическое поведение на сервере не проверялось.)*
6. **HTTPS** локально не настраивался (проверка шла по `http` на loopback); для не-Development cookie помечается `Secure`,
   то есть без HTTPS вне Development она не будет работать.
7. **`AllowedHosts`** = `localhost;127.0.0.1;[::1]`: запросы по другим именам хоста отклоняются фильтром хостов
   (выводится из конфигурации; не проверено запуском).
8. **R-001**: резервного копирования PROD нет — блокирует любую мысль о PROD независимо от кода.
9. **SQL-режим не проверялся на живой TEST-БД** в этой среде: безопасность его реальных запросов подтверждена только
   чтением кода и тестами текстов запросов.

## 7. Чек-лист безопасности для PR

Перед открытием PR ответьте «да» на каждый пункт (или объясните исключение в описании PR):

**Данные и подключения**
- [ ] Нет подключения к `FormulaD`; нет `SQLACCESS` в коде и конфигурации как значения по умолчанию.
- [ ] Не ослаблены и не обойдены проверки `SqlOptions` (флаг TEST, запрет базы `FormulaD`, запрет `sa`/`sa1`).
- [ ] Новый SQL — параметризованный; нет конкатенации пользовательского ввода, `SELECT *`, `NOLOCK`, трёхчастных имён, `USE`.
- [ ] Новая пишущая функция вызывает `IEventLog.Record(...)` и работает атомарно (условный `UPDATE … WHERE`).
- [ ] Для нового SQL-адаптера есть парный test double (`Demo*`) с той же семантикой для автотестов.
- [ ] Нет новых SQL-скриптов, исполняемых против PROD; скрипты DBA помечены как ручные.

**Секреты**
- [ ] В коммите нет паролей, токенов, строк подключения, `.env`, `appsettings.Production.json`, `stand/.run/*`.
- [ ] `git status` просмотрен после `git add`; подозрительные файлы открыты и проверены.
- [ ] Примеры используют заглушки.

**Аутентификация и доступ**
- [ ] Новые эндпоинты находятся под `RequireAuthorization()` (кроме `health/live`).
- [ ] Не расширены условия существования `dev-auth/login`; не добавлен пароль по умолчанию.
- [ ] Ответы и логи не раскрывают хост, базу, строку подключения, учётку, внутренние пути.

**Клиент**
- [ ] Нет `dangerouslySetInnerHTML`, `eval`, записи секретов в `localStorage`.
- [ ] Бизнес-правила не продублированы на клиенте как единственная защита (сервер — источник правды).

**Прочее**
- [ ] Если затронута безопасность — обновлены этот документ и `SECURITY_AND_DEPLOYMENT.md`.
- [ ] Тесты проходят: `dotnet test`, `npx vitest run` (см. [10](10-TESTING.md)).
