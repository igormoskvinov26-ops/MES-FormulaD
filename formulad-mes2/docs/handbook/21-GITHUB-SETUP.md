# 21. Настройка GitHub: параллельная работа и версии

> **Назначение:** пошаговая настройка репозитория на GitHub для нескольких разработчиков, защиты основной ветки и выпуска версий.
> **Для кого:** владелец репозитория (администратор GitHub), руководитель проекта.
> **Почему инструкция, а не файлы:** защита веток, роли и безопасность задаются в интерфейсе GitHub, а не файлами репозитория. Всё, что можно задать файлами (проверки, шаблоны, владельцы кода, выпуск релизов), уже лежит в `.github/`.

## 1. Создание репозитория и первая загрузка

1. На GitHub: **New repository** → имя (в проекте: `WEB-MES-F7`), видимость **Private** (в проекте внутренние документы и конфигурация предприятия), без README и без `.gitignore` (они уже есть в проекте).
2. В локальной копии проекта:

```bash
git remote add origin https://github.com/<владелец>/WEB-MES-F7.git
git push -u origin main
```

После первой загрузки на вкладке **Actions** должен появиться workflow **CI**; на `main` он отработает при следующем пуше или PR.

## 2. Общие настройки

**Settings → General:**

- **Default branch:** `main`.
- **Pull Requests:** оставить включённым только **Allow squash merging** (один коммит в `main` на PR); выключить merge commits и rebase merging; включить **Automatically delete head branches** и **Allow auto-merge**.

## 3. Защита ветки main

**Settings → Branches → Add branch ruleset** (или классическое правило), для `main`:

| Параметр | Значение |
|---|---|
| Require a pull request before merging | включить; **Required approvals: 1** |
| Dismiss stale pull request approvals when new commits are pushed | включить |
| Require review from Code Owners | включить (владельцы — в `.github/CODEOWNERS`) |
| Require status checks to pass | включить; обязательные проверки: **`backend`**, **`frontend`**, **`secrets`**, **`docs`** |
| Require branches to be up to date before merging | включить |
| Block force pushes | включить |
| Restrict deletions | включить |
| Do not allow bypassing the above settings | включить (правила действуют и для администратора) |

Имена проверок появятся в списке после того, как CI отработает хотя бы один раз.

Дополнительно для тегов версий: **Settings → Rules → New tag ruleset** для `v*` — разрешить создание только администраторам и поддерживающим (Maintain), запретить удаление и перезапись тегов.

## 4. Безопасность

**Settings → Code security** (для приватного репозитория часть функций входит в платный план GitHub; если функции нет в вашем плане, обязательной остаётся проверка `secrets` в CI):

- **Secret scanning** и **Push protection** — включить: GitHub не даст отправить пароль или ключ.
- **Dependabot alerts** и **Dependabot security updates** — включить; регулярные обновления зависимостей настроены файлом `.github/dependabot.yml`.
- **Two-factor authentication:** потребовать для всех участников (у организации — в настройках организации).

Проверка `secrets` в CI ищет пароли в **добавленных** строках PR и не заменяет Secret scanning. Правило остаётся прежним: секреты не пишутся ни в код, ни в скрипты, ни в документы (см. [09](09-SECURITY-AND-CONSTRAINTS.md)).

## 5. Люди и роли

**Settings → Collaborators and teams → Add people:**

| Роль GitHub | Кому | Что может |
|---|---|---|
| Admin | владелец | настройки, защита веток, роли |
| Maintain | ведущий разработчик | управление PR, выпуск версий; без опасных настроек |
| Write | разработчики | создавать ветки в репозитории и открывать PR (форки не нужны) |
| Triage / Read | аналитики, тестировщики, наблюдатели | комментировать и заводить issues / только читать |

Когда разработчиков станет несколько, замените `@igormoskvinov26-ops` в `.github/CODEOWNERS` на конкретных людей или команды по областям (например, `/apps/web/` — фронтенд, `/src/` — бэкенд), SQL-слой и `sql/` оставьте за ответственным за данные.

## 6. Как выпустить версию

1. Убедиться, что `main` зелёный (проверки CI прошли).
2. В `CHANGELOG.md` переименовать накопленное в `[Unreleased]` в новый раздел `## [X.Y.Z] — ГГГГ-ММ-ДД` и оставить пустой `[Unreleased]`.
3. Слить это изменение в `main` через PR.
4. Поставить тег на коммит в `main` и отправить его:

```bash
git checkout main && git pull
git tag -a vX.Y.Z -m "FormulaD MES X.Y.Z"
git push origin vX.Y.Z
```

5. Workflow **Release** прогонит тесты, соберёт архив (`formulad-mes-vX.Y.Z.zip`: API и собранный интерфейс) и создаст релиз на GitHub с заметками из `CHANGELOG.md`. Версии `0.x` помечаются как предрелиз. Если раздела `[X.Y.Z]` нет в `CHANGELOG.md`, workflow завершится ошибкой с понятным сообщением.

Правила номеров — в [12](12-DEVELOPER-WORKFLOW.md) (раздел «Версии»). Исправление уже выпущенной версии после пилота делается веткой `release/X.Y` от нужного тега, а не правкой тега.

## 7. Контрольный список после настройки

- [ ] Репозиторий приватный, ветка по умолчанию `main`, разрешён только squash-merge.
- [ ] Защита `main` включена, обязательные проверки: `backend`, `frontend`, `secrets`, `docs`.
- [ ] Прямой пуш в `main` отклоняется (проверить: попытаться отправить тестовый коммит).
- [ ] Тестовый PR показывает четыре проверки и запрашивает ревью у владельца кода.
- [ ] Secret scanning и push protection включены (если доступны в плане), включён Dependabot.
- [ ] Разработчики приглашены с ролью Write, у всех включена двухфакторная аутентификация.
- [ ] Защита тегов `v*` включена.
- [ ] Первый релиз выпущен по шагам раздела 6 и архив скачивается.

## 8. Что делать со старым репозиторием

В прежнем общем репозитории остаются две ветки разработки MES и PR № 1. Он **не изменялся**. После проверки нового репозитория:

- закройте PR № 1 с комментарием, что разработка перенесена в новый репозиторий, а ветки MES оставьте как архив или удалите по решению владельца;
- **смените пароль тестового логина `mes_reader` на сервере базы данных**: в истории старого репозитория он остаётся открытым (в истории нового его нет). Это обязательно, удаление из нового репозитория пароль не отзывает (задача T-001 в [16-BACKLOG](16-BACKLOG.md));
- посторонний проект (Telegram-бот) продолжает жить в старом репозитории независимо.
