## 1. Организация репозитория

- Система — **только** папка `formulad-mes2/`. Остальное в корне (`api/`, `web/`, `scripts/`, `vercel.json`, `.github/workflows/cron.yml`,
  `*.md` в корне) — посторонний проект (Rubl Telegram); его не трогаем и не описываем.
- Корневой `.gitignore` игнорирует `*.png`; `formulad-mes2/.gitignore` дополнительно: `bin/ obj/ node_modules/ dist/ wwwroot/ stand/.run/ .env
  appsettings.Production.json *.tsbuildinfo docs/design/*.webp`; скриншоты `docs/screenshots/*.png` явно разрешены.
- Линтеров, форматтеров (`eslint`, `prettier`, `.editorconfig`) и CI для MES **нет**. Единственные автоматические проверки —
  компилятор, `tsc` и тесты ([10](10-TESTING.md)). Следите за стилем вручную (раздел 3).

## 2. Ветки и коммиты

**Ветки.** Рабочая ветка этой разработки — **`claude/new-session-bizv59`** (на `origin` есть только ветки вида `claude/*`; локальной
ветки `main` в клоне нет — какая ветка считается основной на GitHub, *не подтверждено*). Из этой ветки открывался PR (в сессии — PR № 1;
его текущее состояние не проверялось). Правила:

- Разрабатывайте на выделенной ветке, не пушьте в чужие.
- Если PR ветки уже слит, дальнейшую работу начинайте как **новую** (перенести ветку на актуальную основную, не накладывать коммиты
  на слитую историю).
- **PR не создаётся без явной просьбы владельца.**

**Коммиты.** История папки `formulad-mes2/` (76 коммитов, во всех автор в git — `Claude`) использует «разговорный conventional commits»:

```text
feat(fok): add confirmation modal, queue chevrons, ATV silhouette, banner accent
fix(stand): work on macOS where setsid is missing
test: align three stale expectations with current UI labels
feat(ui): left-to-right fill animation on button hover
add SqlNcpStore — SQL read/write for NCP (tblNCP, tblComponent, tblDiscrepancyList)     ← старый стиль
```

Рекомендации: тип `feat | fix | test | docs | chore | refactor` + область в скобках; тема ≤ 72 символов, **глагол в повелительном
наклонении, по-английски**; тело — **зачем** (а не что), списком; один коммит — одна логическая правка (код + тесты + доки к ней).
Не пропускайте хуки (`--no-verify`), не переписывайте опубликованную историю (`--amend`, `push --force`) без прямой просьбы.

Подпись агента, если коммит делает ИИ (так принято в этой ветке):

```text
Co-Authored-By: <имя модели> <noreply@anthropic.com>
Claude-Session: <ссылка на сессию>
```

Перед коммитом: `git status` и **просмотр того, что попадёт** (`git diff --staged`); добавляйте файлы **по имени**, не `git add -A`.

## 3. Стиль кода

### Backend (C#)

- .NET 10, `Nullable` и `ImplicitUsings` включены; файловые пространства имён (`namespace FormulaD.Mes.Api;`); `record` для DTO;
  первичные конструкторы; `CancellationToken` во всех асинхронных портах.
- Новая возможность = **интерфейс (порт) + Demo-реализация + Sql-реализация + регистрация в обеих ветках `switch (dataSource)`**
  в `Program.cs` (иначе в одном из режимов маршрут пропадёт или не соберётся).
- Эндпоинты — Minimal API в `Program.cs`; валидация на границе; бизнес-отказ — `Problem(title, detail)` (`400`) или `404`;
  успех — `Results.Ok(...)`. Идентификатор пользователя — `user.Identity?.Name ?? "неизвестно"`.
- Каждая операция записи вызывает `IEventLog.Record(...)` и атомарна (условный `UPDATE … WHERE VIN=@vin AND statusid=@from`).
- SQL — только параметризованный, с явным списком колонок, `OFFSET/FETCH`, без `NOLOCK`/`SELECT *`/динамических имён.
- Комментарии — **по-русски, объясняют «почему»** (ограничение, решение РП, ссылка на раздел спецификации), а не «что».
- Соглашение **`ponytail:`** (в коде ≈26 мест): так помечается **сознательное упрощение** с указанием потолка и пути улучшения
  (`// ponytail: SameSite=Strict + проверка Origin вместо antiforgery; добавить antiforgery, если появятся cross-site сценарии`).
  Видите такой комментарий — это известное место роста, а не забытый баг. Добавляйте свои по тому же образцу.

### Frontend (TypeScript/React)

- `strict: true`; функциональные компоненты и хуки; без внешних UI-библиотек (в зависимостях только `react`, `react-dom`, `qrcode`).
- Все HTTP-вызовы — через `api.ts` (единственный `fetch`); ответы типизированы; ошибки — `ApiError`.
- Новые экраны получают `{ session, onNavigate, onLogout }` и рисуют `<AppHeader …/>`.
- Тексты интерфейса — по-русски, в коде; цвет — не единственный носитель смысла (всегда слово/значок рядом).
- Стили: общие — `styles.css`; компоненты F7 — `f7-components.css` (классы `f7mes__*`, `f7plan__*`). Токены и принципы — `08-UI-DESIGN-SYSTEM`.
  Тёмная тема — через `:root[data-theme="dark"]`; **у глобального правила `:root[data-theme="dark"] button` высокая специфичность** —
  новые кнопки с собственным фоном перекрывайте селектором не слабее `:root .scope button.class`.
- Доступность: `aria-label`, `role="status"`, фокус клавиатуры. **Не используйте `clip-path` на элементах с кольцом фокуса без
  компенсации** — клип обрезает `outline` (известная проблема, [13](13-ROADMAP-AND-KNOWN-ISSUES.md)).
- Доступные имена и `aria-label` — часть контракта тестов ([10](10-TESTING.md#7-соглашения)).

## 4. Типовые задачи (рецепты)

### 4.1. Добавить новую операцию с записью

1. Опишите интерфейс/метод в соответствующем порту (`PlanTransitions.cs`, `Ncp.cs`, …); результат — enum исхода.
2. Реализуйте в Demo (мутация в памяти + `IEventLog.Record`).
3. Реализуйте в Sql (параметризованный `UPDATE/INSERT`, условие по статусу, `IEventLog.Record`); проверьте права логина (`sql/create-writer-login.sql`).
4. Зарегистрируйте в **обеих** ветках `switch` в `Program.cs`.
5. Добавьте эндпоинт (`RequireAuthorization()` через группу), валидацию, перевод исхода в `200/400/404`.
6. Тесты: `401` без входа; успех; отказ по статусу/валидации; маршрут существует в `SqlConfiguredFactory`.
7. `api.ts`: типизированный метод; экран; тест экрана.
8. Обновите `04-API-REFERENCE`, `03-DOMAIN-MODEL` (если менялись правила) и **ТЗ-статус** в [01](01-PRODUCT-AND-REQUIREMENTS.md).

### 4.2. Добавить экран

1. Добавьте значение в тип `Screen` и запись в `TABS` (`AppHeader.tsx`: ключ, подпись, иконка, группа).
2. Добавьте `case` в `switch (screen)` в `App.tsx`.
3. Экран принимает `{ session, onNavigate, onLogout }`, рисует `<AppHeader screen="…" …/>`; блок заголовка — как у остальных (`f7plan__title`).
4. Тест экрана по образцу `FokScreen.test.tsx` (`mockFetch`).
5. Проверьте обе темы и свёрнутое боковое меню; соберите (`npm run build`) и пройдите руками на стенде.

### 4.3. Изменить демо-данные

Правьте `fixtures/*.demo.json`; затем прогоните **все** тесты (счётчики и списки зависят от фикстур) и пройдите сценарий из
[00](00-README.md#4-что-посмотреть-руками-сценарий-на-демо-данных).

### 4.4. Добавить изображение/ассет

Положите в `apps/web/public/` (отдаётся из корня). Из-за `*.png` в `.gitignore` добавляйте принудительно:
`git add -f formulad-mes2/apps/web/public/<файл>.png`.

## 5. Definition of Done

Задача завершена, когда выполнено **всё**:

- [ ] Требование прослеживается до пункта спецификации/решения РП; расхождения названы явно (а не «молча» реализованы).
- [ ] Работает **и в Demo, и в Sql** (или явно записано, что Sql-часть не сделана/не проверена).
- [ ] Бизнес-правила соблюдены на сервере; клиент лишь показывает причину.
- [ ] Операции записи пишут в `IEventLog`.
- [ ] Тесты добавлены; **полный** прогон `dotnet test`, `npx vitest run`, `npx tsc -b` — зелёный.
- [ ] UI проверен глазами на стенде: светлая и тёмная темы, развёрнутое/свёрнутое меню, состояния «загрузка/пусто/ошибка».
- [ ] Чек-лист безопасности ([09](09-SECURITY-AND-CONSTRAINTS.md#7-чек-лист-безопасности-для-pr)) пройден; секретов нет.
- [ ] Документация обновлена (затронутые документы справочника; `docs/*.md` — если их содержимое стало ложным).
- [ ] Коммит(ы) понятны, в историю не попали лишние файлы.

## 6. Чек-лист PR

Описание PR должно содержать: **что и зачем**; ссылку на пункт ТЗ/вопрос В-NN; как проверить (шаги на стенде); результаты тестов
(числа); скриншоты UI (обе темы), если менялся интерфейс; известные ограничения; статус по Sql («не проверялся на живой TEST-БД»).

Ревьюер проверяет:

- [ ] Соответствие ТЗ и решениям РП (`SPEC_GAP_ANALYSIS`): нет «самодеятельных» бизнес-правил.
- [ ] Порт/Demo/Sql/регистрация/эндпоинт/тест/клиент — комплект целиком.
- [ ] Чек-лист безопасности из [09](09-SECURITY-AND-CONSTRAINTS.md#7-чек-лист-безопасности-для-pr).
- [ ] Нет лишних абстракций «на вырост», нет закомментированного кода.
- [ ] Подписи UI и тесты согласованы.

## 7. Работа с ИИ-агентом

Правила, выработанные при разработке этого репозитория с ИИ-агентом:

1. **Не коммитить и не пушить без явной просьбы** владельца; PR — только по явной просьбе. Одобрение одного пуша не распространяется
   на следующие.
2. **PROD не трогать никогда** (раздел 1 документа [09](09-SECURITY-AND-CONSTRAINTS.md)): ни подключений, ни запуска `sql/copy-prod-to-test.sql`
   и `export-schema-from-prod.sql`, ни `sa/sa1`. Эти скрипты — для DBA вручную.
3. **Секреты не вводить в чат и не писать в файлы репозитория.** Пароль стенда — только из `stand/.run/credentials`.
4. **Картинки (`*.png`) — через `git add -f`**, иначе не попадут в коммит (корневой `.gitignore`).
5. **Не использовать `pkill -f <шаблон>`**, если шаблон встречается в собственной команде или в команде вызывающей оболочки
   (убивает сам вызов: код 144, обрыв). Останавливайте процессы по PID/порту или через `stand.sh down`.
6. **Не писать фон `&` на составной команде** (`(a && b &)`): в фон уйдёт весь список; ставьте `&` на самой команде.
7. **Прогонять полный набор тестов**, а не только затронутые файлы: поломки «соседних» экранов находятся только так.
8. **Проверять UI глазами** (скриншоты на стенде, обе темы), а не только тестами и типами: тесты не ловят визуальные поломки
   (например, потерю фона у кнопок в тёмной теме из-за специфичности селекторов).
9. **Деструктивные git-команды** (`reset --hard`, `checkout -- .`, `clean -f`, `stash`) — только после `git status` и осознанно;
   команда `git checkout <ревизия> -- .` внутри «разведки» однажды откатила рабочее дерево — не добавляйте такие команды в цепочки.
10. **Не выдумывать данные и правила**: если в спецификации помечено **[В]**, а решения нет — спросить владельца или явно
    записать допущение; неподтверждённое помечать «(не подтверждено)».
11. **Ничего не удалять «для порядка»**: незнакомые файлы и ветки (в т.ч. посторонний проект в корне) — не трогать.
12. **Сообщать фактические результаты**: если инструмент недоступен (нет SQL Server, нет браузера), так и писать, не заявляя «проверено».

## 8. Частые ловушки

| Ловушка | Почему случается | Как избежать |
|---|---|---|
| Новая возможность работает в Demo, а в Sql маршрута нет | Забыта регистрация во второй ветке `switch` | Тест «маршрут существует в `SqlConfiguredFactory`» |
| Demo и Sql ведут себя по-разному | Семантика реализована дважды (пример: блокировка FOK — `PartInstalled=false` vs `Status=1`) | Парные тесты; единое правило в общем коде, где возможно |
| Кнопка без фона в тёмной теме | Глобальное правило `:root[data-theme="dark"] button` специфичнее вашего класса | Селектор `:root .scope button.cls`; смотреть обе темы |
| Кольцо фокуса не видно | `clip-path` на скошенных кнопках обрезает `outline` | Компенсировать (псевдоэлемент/маска) |
| Тест «Unable to find a label …» | Поменяли `aria-label` или текст кнопки | Менять подпись и тест в одном коммите |
| Счётчики в тестах «съехали» | Изменена фикстура | Прогнать всё; искать зависимые тесты по VIN |
| Картинка не попала в коммит | `*.png` в `.gitignore` | `git add -f` |
| Изменения UI не видны на стенде | Не пересобран `wwwroot` | `./stand/stand.sh down && ./stand/stand.sh up` |
| `up` «уже запущен», пароля нет | Сервер запущен вручную | Остановить по PID/порту |
| В документах написано одно, в коде другое | `docs/*.md` отставали (SQL-режим «без записи» и др.) | Верить коду; исправить документ ([13](13-ROADMAP-AND-KNOWN-ISSUES.md#3-расхождения-документов-и-кода)) |
| Ссылки на экран/путь не работают | Нет роутера (`useState`) | Учитывать при дизайне; роутер — отдельная задача |
| Незавершённая правка идёт в `IncomingInspection*.cs` | Крупные файлы (670/810 строк) | Делать небольшие выделения при работе, не «большой рефакторинг» |
