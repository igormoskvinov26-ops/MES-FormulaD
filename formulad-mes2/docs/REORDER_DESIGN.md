# Перестановка порядка запуска (SEQN) — проект операции на будущее

**Статус: реализовано ТОЛЬКО на демо-данных** (в памяти процесса, источник `DataSource=Demo`).
Маршрут `POST /api/v1/production-plan/{vin}/move` создаётся исключительно в демо-режиме:
в SQL-режиме `IPlanOrderEditor` не регистрируется, поэтому пути физически не существует.
Запись в производственную базу по-прежнему запрещена. Документ описывает, как перенести
ту же логику в SQL, когда это будет разрешено.

Ограничения демо-реализации:
- изменения живут в памяти и **пропадают при перезапуске API** — это песочница для проверки сценария,
  а не хранилище;
- нет проверки `rowversion` и журнала перестановок: в одном процессе с одним оператором их нечем
  проверять. Для SQL оба пункта обязательны (см. ниже);
- стрелки работают в пределах текущей страницы: сосед со следующей страницы не виден.
  Для реальных объёмов нужен серверный расчёт соседа.

## Как это работает сейчас в Access (со слов РП, 27.10.2026)

- Порядок запуска в производство задаёт оператор. Изначально он выстроен по плановой дате отгрузки.
- Кнопка «Редактировать порядок» открывает форму плана с кнопками «Вверх» и «Вниз» справа.
- Перемещение меняет число в текущей строке и затем обновляет остальные строки в зависимости
  от направления: при движении вверх строка, на место которой встали, опускается на одну позицию.

## Риски текущей реализации

- `R-02` из аудита (`docs/SPRINT00_ACCESS_AUDIT.md`): несколько отдельных `UPDATE` без общей транзакции.
  Ошибка между ними оставляет план с дырами или дублями в порядке.
- Нет защиты от одновременной работы двух операторов: оба читают старый порядок и пишут поверх друг друга.
- Изменение общей таблицы `tblPlanTemp` из клиента — пересечение сеансов.

## Предлагаемая операция (TO-BE)

Одна серверная операция на один шаг перемещения:

```
POST /api/v1/production-plan/{vin}/move   { "toPosition": 12, "rowVersion": "<rv>" }
```

Шаг вверх/вниз — частный случай той же операции с соседней позицией.

Внутри — одна транзакция:

1. Прочитать текущую строку и её позицию.
2. Проверить, что `rowversion` строки не изменился с момента чтения клиентом;
   иначе вернуть `409 Conflict` — «план изменил другой оператор, обновите экран».
3. Сдвинуть затронутый диапазон и поставить строку на новую позицию (см. ниже). Перенумеровывать
   **весь** план не нужно — только диапазон между старой и новой позицией.
4. Записать в журнал: кто, когда, какой VIN, из какой позиции в какую.

## Как сделать это удобнее, чем в Access (предложение)

**Кто это делает:** отдельный сотрудник за обычным ПК. Сканера и штрих-кодов у него нет,
он работает с номерами позиций, которые видит на экране. Подтверждено РП 27.10.2026.

Проблема кнопок «Вверх»/«Вниз»: перенести изделие на 20 позиций — это 20 нажатий
и 20 изменений в базе.

1. **Отдельный режим «Изменить порядок».** Пока он не включён, строки не двигаются вообще —
   случайно переставить план нельзя. Вход в режим виден по заметной полосе вверху экрана.
2. **Для дальних переносов — попап «Переместить».** Выбрал строку, нажал «Переместить» (или `F2`):
   - в окне видно VIN, модель и **текущую позицию**;
   - поле «Новая позиция» с номером;
   - **предпросмотр одной строкой**: «встанет между № 12 (DEMO-VIN-00012) и № 13 (DEMO-VIN-00013)» —
     оператор видит результат до того, как согласился;
   - `Enter` — переместить, `Esc` — отмена.
   Дальний перенос выполняется одним действием вместо двадцати.
3. **Кнопки «Вверх»/«Вниз» — обязательны и будут использоваться ежедневно** (подтверждено РП).
   Это основной способ для сдвига на одну-две позиции: строка выделена, нажал — она поехала.
   Горячие клавиши `Alt+↑` / `Alt+↓` работают на выделенной строке, выделение **остаётся
   на перемещённом изделии**, чтобы можно было нажать ещё раз подряд. Попап — для дальних переносов.
4. **Каждое перемещение сохраняется сразу,** одной транзакцией. Не «набрал изменений и нажал
   Сохранить»: иначе при закрытии браузера или разрыве связи работа теряется, а два оператора
   получают конфликт на весь пакет сразу. При немедленном сохранении план в базе всегда целостен.
5. **«Отменить последнее перемещение»** — обратный шаг той же операцией. Это заменяет кнопку
   «Отмена» и не требует хранить черновик.
6. **Перемещённая строка подсвечивается** несколько секунд и остаётся в поле зрения.
7. **Журнал перестановок** (кто, когда, какой VIN, из какой позиции в какую) — отдельным экраном.
   В Access такого следа нет, и сейчас невозможно ответить, кто поменял очередь.

Что сознательно **не** предлагается: перетаскивание строк мышью (на длинном плане легко промахнуться)
и поиск цели сканером (у этого рабочего места сканера нет).

## Как выполнять перенос на произвольную позицию

Обмен с соседом годится только для шага вверх/вниз. Для переноса с позиции `A` на позицию `B`
затрагивается весь диапазон между ними, но это по-прежнему **одна транзакция и два запроса**,
а не построчный цикл:

```
-- перенос вверх (B < A): всё в диапазоне сдвигается на одну позицию вниз
UPDATE dbo.tblProductionPlan SET SEQN = SEQN + 1 WHERE SEQN >= @B AND SEQN < @A;
-- перенос вниз (B > A): всё в диапазоне поднимается на одну позицию
UPDATE dbo.tblProductionPlan SET SEQN = SEQN - 1 WHERE SEQN > @A AND SEQN <= @B;
-- затем сама строка
UPDATE dbo.tblProductionPlan SET SEQN = @B WHERE VIN = @vin;
```

Ключевое отличие от Access: это **множественные обновления одним запросом внутри транзакции**,
а не сотни отдельных `UPDATE` из клиента. Промежуточного состояния «половина плана перенумерована»
не существует — либо применилось всё, либо ничего.

Отдельно потребуется решить:

- что делать с изделиями без `SEQN`, если такие найдутся в данных (сейчас экран уводит их в конец);
- разрешено ли двигать изделие, уже запущенное в производство;
- кто имеет право менять порядок (роль) и как это журналируется.

## Инвариант нумерации: пропусков нет

Подтверждено РП 27.10.2026: **нумерация позиций сплошная, пропусков быть не должно.**
Отсюда следует:

- «Позиция N» однозначна — это и значение `SEQN`, и N-я строка сверху. Попапу не нужны оговорки.
- Каждая операция перемещения обязана сохранять сплошность. Обмен с соседом (шаг вверх/вниз)
  и сдвиг диапазона (дальний перенос) этому удовлетворяют по построению.
- Новое изделие из импорта встаёт в конец: `SEQN = MAX(SEQN) + 1`.
- Если изделие удаляется из плана, хвост нужно подтянуть — иначе появится дыра.
- Сплошность стоит закрепить проверкой на стороне сервера (после операции `COUNT(*) = MAX(SEQN)`
  в пределах плана) и регулярным контролем.

**Проверить на TEST перед реализацией** (сейчас фактическое состояние неизвестно):

1. сколько строк с `SEQN IS NULL`;
2. есть ли повторяющиеся `SEQN`;
3. есть ли пропуски в нумерации.

Если расхождения найдутся — потребуется разовая нормализация плана отдельным согласованным
скриптом на TEST (не на PROD) до включения операций перемещения.

Примечание: в демо-фикстуре намеренно оставлено изделие с пустым `SEQN` и разрыв в нумерации.
Схема SQL допускает `NULL` в этом поле, поэтому экран обязан корректно показывать и такие данные,
даже если бизнес-правило их запрещает. Сплошность обеспечивает операция записи, а не экран просмотра.

## Условия, без которых реализовывать нельзя

- Разрешение на операции записи и согласованная модель аутентификации с ролями.
- TEST-база и учётная запись с правом `UPDATE` **только** на нужные столбцы.
- Проверенная совместимость с работающим Access: он продолжит писать в ту же таблицу.
- `R-001` из `docs/SECURITY_AND_DEPLOYMENT.md`: подтверждённое резервное копирование `FormulaD`.
