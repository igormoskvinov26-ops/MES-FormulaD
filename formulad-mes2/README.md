# FormulaD MES 2.0 (F7 MES)

Производственная система учёта сборки квадроциклов: ASP.NET Core (.NET 10) API + React/TypeScript UI на русском языке.
Единственный источник данных — SQL Server. Два окружения: **Development** (тестовая база `FormulaD_TEST` в Docker)
и **Production** (рабочая база `FormulaD` на сервере).

> **Для разработчика:** полный справочник (архитектура, домен, API, фронтенд, тесты, эксплуатация, бэклог, план внедрения) —
> в [`docs/handbook/`](docs/handbook/00-README.md). Начните с `docs/handbook/00-README.md`. План работ —
> [`docs/handbook/20-DEVELOPMENT-PLAN.md`](docs/handbook/20-DEVELOPMENT-PLAN.md); работа командой и GitHub —
> [`CONTRIBUTING.md`](CONTRIBUTING.md). Файлы в `docs/*.md` (кроме `docs/handbook/`) — **историческая документация**
> первых этапов; её статус указан в начале каждого файла.

## Что умеет

Скриншоты после редизайна (светлая и тёмная тема, планшет) — [`docs/screenshots/f7/`](docs/screenshots/f7/README.md).

12 экранов в едином стиле F7 (светлая и тёмная тема, сворачиваемое меню и очередь, режим планшета):

- **Производственный план:** таблица, поиск по VIN (клавиатура и сканер), фильтр по статусу — клик на плашки сводки,
  пагинация, настройка колонок, перестановка порядка, печать JobCard (QR) по одному и пакетно.
- **Импорт плана:** CSV/вставка из Excel → построчная проверка → исправление → публикация в конец очереди.
- **Старт, Завершение, FOK, Rework:** переходы статусов по сканеру; FOK проверяет незакрытые обязательные детали и
  готовность станций (кольцо готовности, нажатие на сегмент); картинка изделия по модели и цвету.
- **Календарь:** ракурсы «День», «Неделя», «Месяц», клик по изделию открывает «Прогресс сборки» (линия станций), перетаскивание карточки (или меню «⋮») меняет порядок запуска в плане (с подтверждением и откатом); посты контроля качества на линии станций настраиваются в администрировании; прогноз выпуска по очереди плана и производительности линии, карточки изделий в днях, отклонение от плановой даты. Выходные, праздники и особые часы дня задаются в шапке дня (⚙, затем «Пересчитать план») и в «Администрирование → Производственный календарь» (загрузка из Excel, ручное редактирование и график работы линии: смена, перерывы, рабочие дни, изделий в смену). Дальше — день, месяц, перенос карточек, прогресс сборки ([`22-PRODUCTION-CALENDAR.md`](docs/handbook/22-PRODUCTION-CALENDAR.md)).
- **Станции:** линия из 11 станций, отметки проверки компонентов, фиксация расхождения (NCP).
- **Несоответствия (NCP):** регистрация, «деталь установлена» и «закрыть заявку» — разные действия, печать листов.
- **Входной контроль:** поставка → Packing List → коробки → результат по строке → закрытие.
- **Отчётность** и **Администрирование** (справочники и производственный календарь).

Журнал событий пишется в память процесса и при перезапуске теряется; эндпоинта для его чтения нет (см. T-005 в бэклоге).
Состав API — 49 эндпоинтов, описание — [`docs/handbook/04-API-REFERENCE.md`](docs/handbook/04-API-REFERENCE.md).
Аутентификация — только dev-режим (включается явно, только в Development, только на loopback, пароль из env/user-secrets);
реальных учётных записей и ролей пока нет (веха M4 плана).

## Требования

- .NET SDK 10.0
- Node.js 20+ (проверено на 22)
- SQL Server (Docker — для разработки, реальный сервер — для прода)

## Тестовый стенд (одной командой)

Стенд на тестовой базе `FormulaD_TEST` в Docker: собирает UI и API, запускает и проверяет, что всё живо.
Перед запуском стенда поднимите Docker-базу ([`docker/`](docker/README.md)).

```bash
./stand/stand.sh up       # сборка, запуск на http://localhost:5080, печать логина и пароля
./stand/stand.sh smoke    # 11 проверок: health, 401 без входа, вход, план, NCP, VIN, статика
./stand/stand.sh status   # работает ли стенд
./stand/stand.sh down     # остановка
```

Пароль генерируется на каждый запуск (или задайте `STAND_PASSWORD`), хранится в `stand/.run/credentials`
(в git не попадает). Порт — переменная `PORT`, пользователь — `STAND_USER`. Требуются .NET SDK 10, Node.js 20+, curl.

## Запуск (macOS / Linux)

### Быстрый запуск (рекомендуется)

```bash
./stand/stand.sh up        # собирает UI + API, запускает, печатает логин и пароль
```

Откройте http://localhost:5080, войдите напечатанными логином и паролем. Пароль хранится в `stand/.run/credentials`.

### Ручной запуск (два терминала)

**Терминал 1 — API:**
```bash
cd src/FormulaD.Mes.Api
dotnet user-secrets set "Sql:ConnectionString" \
  "Server=localhost;Database=FormulaD_TEST;User ID=<login>;Password=<...>;Encrypt=True;TrustServerCertificate=True"
DevAuth__Enabled=true DevAuth__Username=admin DevAuth__Password=F7mes \
  dotnet run --urls http://localhost:5080
```

**Терминал 2 — UI (dev-сервер):**
```bash
cd apps/web && npm install && npm run dev
```

Открыть **http://localhost:5173** (не 5080), войти: логин `admin`, пароль `F7mes`.
Vite проксирует `/api` на `http://localhost:5080`.

> При ручном запуске фронт обслуживается Vite на порту 5173. Чтобы обслуживать всё
> с одного порта (5080), соберите UI: `cd apps/web && npm run build` — Vite положит
> файлы в `src/FormulaD.Mes.Api/wwwroot`, и API отдаст их напрямую.

### Остановка

`Ctrl+C` в каждом терминале (или `./stand/stand.sh down`). Фоновых служб, портов брандмауэра и установок в систему проект не создаёт.

## Подключение к базе данных

Приложение подключается к SQL Server. Строка подключения задаётся через `dotnet user-secrets` или
переменные среды — **в репозитории строк подключения нет и быть не должно**.

```bash
cd src/FormulaD.Mes.Api
dotnet user-secrets set "Sql:ConnectionString" \
  "Server=<host>;Database=<db>;User ID=<login>;Password=<...>;Encrypt=True"
```

Для записи нужен логин с правами `INSERT`/`UPDATE`/`MERGE` (см. `sql/create-writer-login.sql`),
для чтения — логин с `SELECT`. Локальную копию базы в Docker из резервной копии, снятой
владельцем/DBA, поднимает [`docker/`](docker/README.md).

**Приложение содержит код записи** (`UPDATE`/`INSERT`/`MERGE`: переходы статусов, перестановка и импорт плана, NCP, отметки
станций, входной контроль, отметка печати; для входного контроля — ещё и `CREATE TABLE`).

## Тесты

```bash
dotnet test                      # из корня репозитория (бэкенд)
cd apps/web && npm run test      # vitest
cd apps/web && npm run build     # tsc + vite build
```

Бэкенд-тесты используют in-memory реализации (test doubles) вместо SQL — базы данных для запуска тестов не нужно.
Сквозные тесты (Playwright, на стенде) — [`docs/handbook/10-TESTING.md`](docs/handbook/10-TESTING.md#сквозные-тесты-e2e-playwright).

CI на GitHub дополнительно измеряет покрытие и проверяет пороги (бэкенд ≥ 50% строк, фронтенд ≥ 80%), ищет секреты в
добавленных строках и битые ссылки в документации.

## Структура

```text
src/FormulaD.Mes.Api/      ASP.NET Core Minimal API (домен, SQL-источник данных, endpoints)
tests/                     интеграционные тесты API (xunit, in-memory test doubles)
apps/web/                  React + TypeScript + Vite
fixtures/                  тестовые данные (используются test doubles в тестах)
sql/                       скрипты DBA (создание базы, логины, копия из PROD) — выполняет человек, не приложение
docker/                    локальный SQL Server с восстановлением резервной копии как FormulaD_TEST
deploy/                    установка службы Windows и пример конфигурации
stand/                     тестовый стенд одной командой
scripts/                   проверки CI (секреты, ссылки, покрытие)
docs/handbook/             справочник разработчика; остальной docs/ — историческая документация
```

## Ограничения

Это не промышленная MES: нет реальной аутентификации и ролей, журнал событий в памяти,
нет связи входного контроля с допуском в производство (В-33 не согласован), нет отчётов за период. Что и в каком порядке
делается — [`docs/handbook/20-DEVELOPMENT-PLAN.md`](docs/handbook/20-DEVELOPMENT-PLAN.md).
